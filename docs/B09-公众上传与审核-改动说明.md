## 一、这轮做了什么（一句话）

访客可以在「我要投稿」页投稿（需登录、只收 PDF），投稿进入**待审核**状态
（不进书架、搜不到、下载不了）；老师在后台「投稿审核」队列里**通过**（真进知识库）
或**退回**（必填理由）；投稿人在「我的投稿」里随时看到状态与退回理由。

至此任务书五件事的进度：**反馈 ✅ / 分享 ✅ / 公众上传 ✅ / 审核全链路 ✅ / 咨询推荐页（等韶茹可行性结论，未动）**。

## 四、两个设计决定（组长评审时重点看这两条）

### 1. 投稿数据为什么用 JSON 而不是 Prisma

任务书草案写的是「Prisma 新增 `Contribution` 模型」，实际**没有**这么做，原因：

1. `backend/prisma/schema.prisma` 是 B02（月月）的文件，分工硬约束写着
   「不重构别人的文件（要改先在群里说）」；
2. 投稿数据是**运行时数据**，和 `backend/data/track/events.jsonl` 同类，本来就在
   gitignore 范围，不属于要进仓库的 schema；而且里面存投稿人姓名/机构/电话，
   更不该进 git；
3. 演示期投稿量在几十条量级，JSON 全量读写代价可以忽略；写操作已用 Promise 链
   串行，不会互相覆盖。

**字段名刻意与任务书里的 Prisma 草案对齐**（`id/userId/userName/userOrg/userPhone/
title/org/year/type/tags/note/fileName/storedName/size/status/reason/docId/createdAt/
reviewedAt`）。组长若要求并进数据库，照字段搬即可，六个接口的出入参**一个都不用改**。

### 2. 「通过」为什么不直接调引擎

知识库入库的口径、标签写入、列表缓存失效三步都写在 `admin.ts` 的
`POST /api/admin/knowledge/upload` 里。审核接口**内部转发给那个接口**（带
`X-Admin-Token`），是唯一既不重复实现、又不改别人文件的做法。

由此得到一条铁律（任务书验收第 6 条）：**入库失败时状态必须停在 `pending`**。
实测：引擎没起时点「通过」→ 返回 502 +「入库失败，投稿状态仍是待审核：连不上知识库引擎」，
投稿人那边看到的仍是「待审核」。管理员重新点一次即可，不会出现「假通过」。

- 引擎入库有**几秒到几分钟**延迟，通过后别立刻断言「书架一定有」（与老师后台上传同一表现）。
