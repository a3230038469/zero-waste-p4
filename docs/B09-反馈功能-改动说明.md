## 三、技术口径（写给对接的人）

**数据怎么进库**：走已有的 `POST /api/track`，事件名用白名单里现成的 `feedback_submit`
（真相来源 `backend/src/track/types.ts`，**未改一行**）。payload 形状：

```json
// 资料级（scope="doc"）
{ "kind": "doc", "docId": "k-16", "docTitle": "城市垃圾分类指数2020-2025", "reason": "broken", "text": "第 12 页翻不开", "contact": "" }

// 站点级（scope="site"）
{ "kind": "site", "reason": "usage", "text": "……", "contact": "", "path": "/" }
```

- `reason` 取值（**改它 = 改数据口径**，要同步本文档）：
  - 资料级：`broken` 文件打不开 / `wrong` 内容有误 / `duplicate` 重复收录 / `missing` 希望补充
  - 站点级：`feature` 功能建议 / `content` 内容建议 / `usage` 使用问题 / `other` 其他
- 留言上限 300 字（payload 整体限 4000，留足余量）；联系方式 60 字。
- 站点级留言**必填**、资料级选填 —— 站点反馈的价值全在文字里，资料反馈只勾原因也有用。

**两个已知的边界（说在前头，不是缺陷隐瞒）**：
1. 埋点是「尽力而为」的旁路（`api/track.ts` 的设计）：网络异常时**用户仍会看到提交成功**，这条会丢。
   要强一致就得加 `POST /api/feedback` 独立接口 —— 属于加接口，需先在群里拍板，本次没做。
2. 反馈内容目前只能进看板计数（`feedback_submit`），**没有后台列表逐条看**。
   建议 10/15 迭代记录里排期（读 `events.jsonl` 按 event 过滤即可，不需要新存储）。

## 五、为什么这样设计（给评审的两句话）

1. **不新增接口**是刻意的：任务书硬约束「不引新依赖、不动别人的文件」，且埋点白名单当初就为反馈留了位 —— 用现成的路，改动面最小，组长合并最省心。
2. 入口放在**引用提示下方**而不是主操作行：反馈是低频动作，不该和「预览 / 下载」抢视觉；但「低调」不等于「藏起来」，详情页和页脚各一处，够找。
