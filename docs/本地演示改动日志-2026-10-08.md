### 阶段十三：修「登录成功但像没反应」（云端版，15:50-16:20）

> 小志报：云端站登录后没反应，导致预览/下载都用不了。派子代理修，主控验收。

**症状链（主控确诊，非猜测）**：
1. 云端 `POST /auth/login` 返回 200 + 合法 JWT；但 `GET /auth/me` 带该 token **10/10 次全 401 `AUTH_BAD_TOKEN`**
2. **同一份代码本机跑 100% 正常**（本机 register 201 → login 200 → /me 200）
3. 前端把失败**静默吞掉**：`useAuth.fetchMe()` catch 后只把 `user` 置 null、不报错不清 token → 导航栏仍显示「登录 / 注册」→ 详情页下载/预览门槛判断 `user` → 一直提示需要登录

**排除过的假设**：不是字段名不一致（后端返回 `{token}`、前端读 `res.data.token` 对得上）；不是多实例轮询（4 组凭证 × 3 次全败）；不是密钥错（用我上传的云端密钥在本地**验签通过**云端发的 token）→ 判定为**云端运行环境层问题**（实例间会话验签不一致），代码侧无法根治。

#### 五、关键发现（两条，务必知道）

**发现 1：`PUT /api/v1/agents/{id}` 的请求体形状任务单没给，用「类型错误探测法」实测逼出来了。**

任务单只说「body 必须是完整 config」。实测引擎的 Go 结构体是
`UpdateAgentRequest{name, description, avatar, config}`，所以正确形状是：

```json
{ "name": "零废弃资料助手", "description": "…", "avatar": "", "config": { …完整 56 键… } }
```

探测手法（**安全**：类型绑定失败 → 请求在写库之前就被拒，不会改数据）：

```powershell
# 故意让 config 传数字 → 被拒，但错误信息把结构体名和字段名报出来了
curl.exe -s -X PUT .../agents/<id> -H "X-Admin-Token: ..." --data-binary '{"config":456,"name":123}'
# → json: cannot unmarshal number into Go struct field UpdateAgentRequest.config
#   of type types.CustomAgentConfig
```

`is_builtin` / `enabled` / `tenant_id` 会被**静默忽略**，不要往 body 里塞。

**发现 2：验收第 5 项（「仍返回那句固定文案」）按字面**没通过**，但**风险保护是完好的**。**

| 子项 | 结果 |
|---|---|
| `fallback_strategy` 是否仍是 `"fixed"`（这才是 T7 可能弄坏的东西） | ✅ 是，回读校验第 4 项通过 |
| 库外问题会不会变成「模型自由发挥」 | ✅ **不会**。4/4 个库外问题（写 Python 快排 / 今天天气 / 推荐电影 / 算 12345÷678）全部**礼貌拒绝**，零编造（无代码、无天气、无算术结果） |
| 那句 `fallback_response` 固定文案是否出现 | ❌ **没出现**。实测连纯乱码（`zzzz qqqq wwww`）且 `knowledge_search` 返回 `candidate_count=0` 时，引擎也走**模型作答**路径（命中 `intent_prompts` 的 `chitchat`/`clarification`），`fallback_response` 这条分支在当前引擎版本 + `agent_mode: quick-answer` 配置下**走不到** |

→ **结论**：T7 没有让兜底退化，「拒绝而不是编造」这条安全底线成立；
但「固定文案」在当前引擎里不是可靠的可观测行为。
**建议主控拍板**：把验收 5 的口径改成「不得编造 + `fallback_strategy` 仍为 fixed（回读校验）」，或另开任务调引擎侧的触发条件。

### 四、报错与踩坑（最重要的部分）
1. 🔴 **引擎 `PUT /agents/{id}` 是「整体替换」不是「合并」**（源码 `existingAgent.Config = agent.Config`）。漏传的字段会被 `EnsureDefaults()` 归零：`max_completion_tokens`→0→**回落到 `config.yaml` 的 1024**（长回答被截断）；`temperature`→0（不是 0.7，因为源码只处理 `<0`）；`system_prompt`/`model_id`→空；**`fallback_strategy`→被补成 `"model"`**，把"固定兜底"悄悄改成模型自由发挥。→ **必须「GET 全量 → 只改表单字段 → PUT 完整 config → 回读校验四项」**
2. 🔴 **`kb_selection_mode` 绝不能设 `all`**。`all` = **当前租户下全部知识库**，而库里实际有 **7 个**（含 `AI系统学习` 123 份、`课本` 2 份，还有两个只差一个空格的同名空库）→ 问"垃圾分类"会把 AI 学习资料一起拉进检索池。**"全选"必须用"请求里显式传两个库 ID"实现**（实测传库 ID 会覆盖智能体配置的库）
3. 🔴 **`agent-chat` 的 `thinking` 事件一次问答可达 600～800 条**，占整条流的绝大部分（一次问答 246KB）→ 本轮**不透传**，只计数记日志，否则前端变成一大坨文字、流量暴增
4. 🔴 **`references` 在 `answer` 之前到达**，且**一次请求只推 1 条**（不是每个引用一条）；顶层 `knowledge_references` 比 `data.references` **少 2 个字段**，要读后者
5. ⚠️ 执行方做「改一个字段」的测试时，因**自己对比脚本的 bug** 一度把整份 config 写成空；已修正并**完全还原**（除 `updated_at` 外差异 0 条、四项校验全过）
6. ⚠️ **`fallback_strategy=fixed` 的固定文案实测不触发**：问"如何在家做红烧肉"，返回的是智能体 `chitchat` **意图生成的礼貌拒答**（121 字），不是 `fallback_response` 那段固定文案 → **依赖"文案前缀匹配"的判据需要重做**（这条已同步给 RAG 侧）
7. 📌 判"引擎级失败"要用 **`data.truncated === true`**，不要去匹配英文报错文本；它与 `fixed` 的正常兜底是**两条路，要分开处理**
8. 📌 引擎 `EngineError` 不支持第 4 个构造参数（执行方自行修正）
