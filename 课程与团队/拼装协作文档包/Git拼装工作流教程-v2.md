# Git 拼装工作流教程（GitHub 版 · 配合《拼装式开发方案 v1.0》使用）

> **适用对象**：P3P4组宽益工坊全体成员，**零基础**  
> **读完你能做到**：领任务 → 拉代码 → 改自己那块 → 交上去 → 拼进产品  
> **核心认知**：你们做的东西最终拼在 GitHub 仓库的 `main` 主干上。**你的代码只有"合入 main"才算交付。**  
> **版本**：v2.1（2026-10-01）
>
> **📌 不想学命令行？** 不用学——日常交付走《成果上GitHub-WorkBuddy全员交付教程》的**姿势 A（网页拖拽，零命令）**&#x5373;可，本教程可以跳过。本教程是给想学命令行姿势的同学的，功能上和姿势 A 完全一样，只是快一点。

---

## 〇、全景图：你每天的工作流（先看懂这个）

```
① 打开 GitHub 看板，领一个任务（Issue）
        ↓
② git pull 拉最新代码
        ↓
③ 开一个自己的分支，改代码
        ↓
④ git push 推上去 + 发起 Pull Request（"我做完了，请检查"）
        ↓
⑤ 集成负责人审核 → 合并进 main
        ↓
⑥ 你的小块，正式拼进产品 ✅
```

**记住一句话：不做完 ⑤，你的活就不算干完。**

## 一、第一次准备（每人只做一次，约 15 分钟）

### 1.1 装 Git

- **Windows**：<https://git-scm.com/download/win> 下载，安装时一路"下一步"。装完右键桌面能看到 **"Git Bash Here"** 即成功
- **Mac**：终端输入 `git --version`，按提示安装

### 1.2 报身份（一次性）

```bash
git config --global user.name "张三"        # 你的真名，方便追溯
git config --global user.email "你的邮箱"
```

### 1.3 注册 GitHub + 进仓库

1. 注册 <https://github.com> 账号
2. **把你的 GitHub 用户名发给集成负责人**，他把你加进 `widework` 私有仓库
3. 收到邮件邀请，点接受

### 1.4 把项目拉到本地（一次性）

```bash
git clone https://github.com/组织名/widework.git
cd widework
```

之后每天开工不需要再 clone，只在本地这个文件夹里干活。

## 二、领任务（GitHub Issues = 任务池）

### 2.1 怎么领

1. 打开仓库 → **Issues** 页签 → 筛选标签 `状态/待领取`
2. 挑一个和自己能力匹配的（看 `难度` 标签：入门/中/高）
3. 认领动作 = **三步**：
   - 点 **assign yourself**（右上角）
   - 把 `状态` 标签从"待领取"改成"进行中"
   - 评论一句"我认领"（留痕，避免撞车）

### 2.2 领取规则（全组统一）

| 规则            | 说明                  |
| ------------- | ------------------- |
| 一人最多 2 个"进行中" | 干完再领                |
| 72 小时无提交自动释放  | 集成负责人收回任务，无损面子      |
| 干不了随时弃坑       | Issue 里评论"释放"即可     |
| 跨组随便领         | 不分 P3/P4、A/B，看板全局可见 |

### 2.3 Issue 里有什么（领之前看清楚）

每个任务 Issue 都写死了四样东西：**任务说明、交付物目录、验收标准（≥3 例）、接口依赖**。**照着做就行，不用问人。** 如果发现 Issue 里缺信息，直接在 Issue 里评论提问。

## 三、每天干活：5 个命令（核心章节）

### 3.1 开工：先拉最新

```bash
cd widework
git checkout main          # 切到主干
git pull                   # 拉下别人昨天合入的所有代码
```

> ⚠️ **这步最重要**：不 pull 就开工 = 大概率和别人冲突，返工的是你自己。

### 3.2 建自己的分支

```bash
git checkout -b feat/12-F1-login-page
```

**分支命名规则：`feat/{Issue号}-{板块}-{简述}`**（Issue 号就是任务编号，例子里是 12）。用这个规则，GitHub 能自动把你的分支和任务关联起来。

### 3.3 改代码

正常写代码、改文件，随时保存。**只改你任务里写的那个目录**，别的地方别碰——这是拼装秩序的底线。

### 3.4 提交（每完成一小步就提交一次）

```bash
git status                     # 看看自己改了啥（提交前必看）
git add .                      # 打包全部改动
git commit -m "feat: 完成登录页表单校验"
```

提交信息格式：`feat: 干了什么`（新功能）/ `fix: 修了什么`（修 bug）/ `docs: 改了文档`。

### 3.5 推上去 + 发 PR（交卷）

```bash
git push -u origin feat/12-F1-login-page
```

推完终端会显示一个链接，点它（或去仓库网页点 **"Compare & pull request"**）：

1. 标题写：`feat: 登录/注册页开发 #12`（**#12 = 任务号，合并后自动关闭任务**）
2. **勾选 PR 模板里的"契约对照清单"**（重点看：你用到的 API 字段名是否和 `docs/contracts/C3` 完全一致）
3. 点 **Create pull request**

**然后等审核。** 集成负责人可能提修改意见——改法：继续在本地改 → `git add .` → `git commit -m "fix: 按评审意见修改"` → `git push`，PR 会自动更新。

## 四、在 WorkBuddy 里干活的同学：产出怎么进 GitHub

**重要事实**：WorkBuddy 沙箱**无法直连 github.com**（实测网络不通）。所以如果你习惯在 WorkBuddy 里用 AI 写代码，流程是：

```
在 WorkBuddy 项目组里干活（AI 生成/修改代码）
        ↓
把产出文件下载到你的电脑（找到任务对应的目录放进去）
        ↓
在电脑上执行 git add / commit / push（就是第三章那套）
```

也就是说：**WorkBuddy 负责"生产"，本地 Git 负责"交付"**。两边各司其职，不冲突。

> 💡 提示：在 WorkBuddy 里让 AI 生成代码时，直接把任务 Issue 的"验收标准"和 `docs/contracts/` 的契约内容贴给它，产出一次到位的概率高很多。

## 五、PR 合并的三道关（为什么你的 PR 还没被合）

| 关         | 谁把关  | 查什么                  |
| --------- | ---- | -------------------- |
| ① CI 自动检查 | 机器   | 代码能不能编译、测试过不过。红了先自己修 |
| ② 契约对照清单  | 你自己勾 | 用到的接口字段/事件名和契约文档是否一致 |
| ③ 集成负责人审批 | 人    | 接口符合性、有没有越界改别人的目录    |

**被要求修改 ≠ 你做得差**，拼装式开发里返工一两次是常态，按意见改完再 push 即可。

## 六、常见报错急救

| 报错                        | 原因        | 解法                                                               |
| ------------------------- | --------- | ---------------------------------------------------------------- |
| `failed to push`          | 别人先推了     | `git pull` 再 `git push`                                          |
| `conflict: both modified` | 你和别人改了同一行 | 把冲突文件打开，找 `<<<<<<<` 标记，保留正确内容，删掉标记，再 add/commit/push。不确定就 @集成负责人 |
| `not a git repository`    | 没在项目文件夹   | `cd widework`                                                    |
| `permission denied`       | 没被加进仓库    | 找集成负责人                                                           |
| 改乱了想重来                    | 手滑        | `git checkout -- 文件名`（丢弃未提交改动）；实在不行重新 clone，云上的都在                |

**终极保命**：最坏情况 = 本地全毁。重新 `git clone` 一次，一切照旧。**你在 GitHub 上的东西不会丢。**

## 七、三条铁律（背下来）

1. **开工先 `git pull`** —— 避免九成冲突
2. **只改自己任务目录里的文件** —— 越界 = 拼装事故
3. **合入 main 才算交付** —— 推了分支不等于干完了
