# 零废弃数字化知识库「对外版」拼装式开发方案

> **版本**：v1.0（2026-10-01）  
> **适用**：AI 向善实战营第四期 · P3P4组宽益工坊  
> **上游依据**：《Week1-P3P4组宽益工坊-PRD需求文档》（0929 版，R01–R14 需求、11 个页面、10/8 demo、10/22 结项）  
> **取代**：《拼装容器与接口契约-说明与方案 v0.1》中"容器选型待定"的部分；拼装地图模板继续沿用  
> **一句话**：**门户自己写、引擎用开源、契约先冻结、中心管合并、任务自己领——保证每人做完的小块一定能拼成一个产品。**

## 〇、方案一页纸（先看这个）

### 总体架构：门户 + 引擎 + 粘合层

```
外部用户（公益从业者/研究者/公众）
        │ 链接访问
        ▼
┌─────────────────────────────────────┐
│  门户站点（我们自己写，公网）           │
│  ├─ 前端：11 个页面（Vue3）            │
│  └─ 轻后端：登录/书架/检索/预览/下载/埋点 │
│        │                             │
│        │ 粘合层：rag-proxy（唯一出口）   │
│        ▼                             │
│  WeKnora 引擎（开源，内网部署）         │
│  解析→切片→向量化→混合检索→重排→生成     │
│        │                             │
│        ▼                             │
│  大模型：Qwen（阿里云百炼，已购套餐）     │
└─────────────────────────────────────┘
```

**核心思想**：

1. **AI 问答引擎不自研**——用腾讯开源的 WeKnora（MIT 许可，支持百炼 Qwen），工作量从"造轮子"降为"装轮子"
2. **门户自己写**——登录、书架、检索、预览、下载这些 PRD 里的 P0 功能，用轻量技术栈（Vue3 + FastAPI），按页面/接口切小块分给个人
3. **粘合层收口**——门户后端只留**一个模块**（rag-proxy）对接 WeKnora，接口改了只改一处

### 拼装保障五件套（本方案的灵魂，详见第五章）

| # | 机制          | 一句话                            |
| - | ----------- | ------------------------------ |
| 1 | **契约冻结**    | 数据字段、API 格式先写死，10/4 后改要走变更     |
| 2 | **Mock 先行** | 前端不等后端、后端不等引擎，人人可并行开工          |
| 3 | **目录即边界**   | 模块之间只许走接口，不许直接伸手，CI 自动查        |
| 4 | **PR 闸门**   | 机器检查 + 契约对照清单 + 集成负责人审批，三关缺一不可 |
| 5 | **每日集成**    | 固定时间合并主干、部署测试环境，集成债不过夜         |

## 一、产品拆解：这个产品由哪几块拼成

### 1.1 从 PRD 到板块的映射

PRD 定义了 14 条需求（R01–R14）、11 个页面、10/8 demo 节点。按"能独立开发、独立验收、最后可拼装"的原则切成 **7 个板块（F0–F6）**：

| 板块     | 名称     | 干什么                            | 覆盖 PRD 需求                       | 自研 or 开源                |
| ------ | ------ | ------------------------------ | ------------------------------- | ----------------------- |
| **F0** | 地基与契约  | 仓库、CI、契约文档、Mock、部署编排           | 全局                              | 自建（集成负责人独占）             |
| **F1** | 前端门户   | 11 个页面                         | R01 R02 R03 R06 R07 R08 R09 R12 | 自研（Vue3 + Element Plus） |
| **F2** | 门户后端   | 登录/文档/埋点/统计 API                | R01 R03 R04 R09 R11 R12 R13     | 自研（FastAPI）             |
| **F3** | RAG 引擎 | WeKnora 部署、400+ 文档导入、调参、API 对接 | R05（A/B/C/D/E 全部）               | **开源 WeKnora**          |
| **F4** | 内容管道   | 钉钉导出 → Excel 元数据清洗 → 批量入库      | R14、内容治理 §9                     | 脚本（Python）              |
| **F5** | 统计看板   | 埋点采集 + 数据看板页                   | R04、§8 八事件                      | **开源 Umami** + 自研看板页    |
| **F6** | 部署运维   | Docker Compose 编排、域名、HTTPS     | N01–N07                         | 自建 + Nginx              |

**每个板块再往小切**：F1 按页面切（1 页面 = 1 小块 = 1 任务），F2 按接口切（1 组 API = 1 小块）。**小块就是 GitHub 上的一个 Issue**，详见第七章。

### 1.2 为什么这样切（而不是按 P3/P4 切）

- **按功能切而不是按组切**：任何组的人可以领任何板块的任何小块，不浪费人力，天然支持"自动领任务"
- **引擎独立成板块**：WeKnora 是现成的，F3 的本质是"部署 + 配置 + 对接"，不需要写多少代码——**这块可以由非技术背景的同学负责**（跟着文档点点点）
- **门户轻量**：PRD §2.4 明确"不做全文检索，仅搜文件名"——所以连搜索引擎都不用装，SQL 模糊查询就够，后端极薄

## 二、开源选型：不重复造轮子

### 2.1 RAG 引擎：WeKnora（你点名的，核实结果很好）

**核实结论（2026-10-01）**：

| 核实项  | 结果                                                                            |
| ---- | ----------------------------------------------------------------------------- |
| 项目   | github.com/Tencent/WeKnora，微信对话开放平台核心框架开源                                     |
| 许可证  | **MIT**（可自由使用、修改、商用，无附加条款）                                                    |
| 当前版本 | v0.8.2（2026-09-24 发布，迭代活跃）                                                    |
| 部署   | Docker Compose 一键部署：`git clone → cp .env.example .env → docker compose up -d` |
| 自带能力 | Web 管理界面 + REST API（`/api/v1`）+ CLI + 官方 MCP Server                           |
| 检索   | **BM25 + 向量混合检索 + 重排 + 引用溯源**（答案附原文出处，可点开核对）                                  |
| 文档解析 | PDF、Word、TXT、Markdown、图片 OCR（PaddleOCR）——覆盖你们 400+ 份资料格式                      |
| 模型接入 | **27 家内置厂商，含 Qwen（阿里云百炼）、DeepSeek、OpenAI、Ollama 本地模型**                        |
| 存储   | PostgreSQL（ParadeDB + pgvector）+ Redis                                        |
| 安全   | 自带登录认证、AES 加密、多工作区 RBAC                                                       |

**与 PRD 需求的对照**——WeKnora 直接吃掉 PRD 里最难啃的部分：

| PRD 需求                              | WeKnora 能力                    | 结论                  |
| ----------------------------------- | ----------------------------- | ------------------- |
| R05 AI 智能问答（P0 核心）                  | RAG 问答、多轮对话（R05-E）、引用溯源       | ✅ 全覆盖               |
| R05-B 自建 RAG 管线（解析→切片→向量化→检索→编排→生成） | 完整流水线全部内置                     | ✅ 全覆盖               |
| R05-C 混合检索（向量+BM25+重排）              | BM25 + dense 混合检索 + reranking | ✅ 全覆盖               |
| R05-D Agent 化                       | ReAct Agent（额外能力，可不用）         | ✅ 超出需求              |
| R06 模糊提问优化                          | 零结果兜底可配置                      | ⚠️ 部分，前端配合          |
| 大模型对接                               | 内置阿里云百炼 Qwen                  | ✅ **正好用上你们已购的百炼套餐** |
| R13 管理后台（P2）                        | 自带知识库管理界面                     | ✅ **内容管理员直接用现成的**   |

**两个额外红利**：

1. **PRD §11.1 说"内容运营与审核归基金会"**——WeKnora 自带的管理界面就是给基金会管理员用的，导入文档、维护知识库都是图形界面点点点，**R13 管理后台基本白送**
2. **PRD 冲突 A 的"AI 答不上来"问题**——WeKnora 回答带引用，答不上来时前端可引导到检索兜底

**一条重要限制（官方安全建议）**：WeKnora 建议部署在**内网**，不要直接暴露公网。这正好和我们的架构吻合——**公网只暴露门户，引擎藏在内网，门户后端做代理**。

### 2.2 备选对比（为什么最终选 WeKnora）

| 方案          | 许可证               | 优势                                  | 劣势             | 结论       |
| ----------- | ----------------- | ----------------------------------- | -------------- | -------- |
| **WeKnora** | MIT               | 混合检索+重排+引用、中文生态、支持百炼 Qwen、Docker 一键 | 项目较新（v0.8.x）   | ✅ **主选** |
| RAGFlow     | Apache 2.0        | 深度文档理解、解析能力强                        | 组件重、资源占用高      | 备选       |
| FastGPT     | Apache 2.0        | 知识库问答成熟                             | 偏工作流编排         | 备选       |
| Dify        | Apache 2.0（有品牌条款） | LLM 应用编排全                           | 偏平台化，定制门户要二开   | 不选       |
| MaxKB       | GPL v3            | 上手快                                 | GPL 传染性许可，商用顾虑 | 不选       |

### 2.3 门户技术栈与配套组件（全部选商用友好的许可）

| 需求       | 选型                           | 许可证                       | 为什么                                               |
| -------- | ---------------------------- | ------------------------- | ------------------------------------------------- |
| 前端框架     | Vue 3 + Vite                 | MIT                       | 国内普及度最高，招人/找资料最容易                                 |
| UI 组件库   | Element Plus                 | MIT                       | 表格/表单/弹窗全都有，不用手写                                  |
| 管理页模板    | 参考 soybean-admin（MIT）        | MIT                       | 看板页可以直接基于它改                                       |
| 门户后端     | Python FastAPI               | MIT                       | 代码量小、自带 API 文档（/docs），联调神器                        |
| 数据库      | SQLite（demo）→ PostgreSQL（正式） | 公共领域 / PostgreSQL License | demo 零配置，正式版跟 WeKnora 同栈                          |
| PDF 在线预览 | PDF.js（Mozilla）              | Apache 2.0                | 前端直接渲染，不用服务器转码                                    |
| Word 预览  | kkFileView                   | Apache 2.0                | 若需要；PDF 为主可先不做                                    |
| 网站统计     | **Umami**                    | MIT                       | **自托管、无 Cookie、隐私友好**——符合公益机构调性，PRD §8 的 8 个事件可映射 |
| 反向代理     | Nginx + Let's Encrypt        | BSD-2 / 免费                | HTTPS 一条命令                                        |
| 全部编排     | Docker Compose               | —                         | 一台服务器 `docker compose up` 全起                      |

> **选型原则**：许可证全部 MIT / Apache 级别（公益项目无法律风险）；能 Docker 部署的不裸装；中文文档优先。**全程没有一个组件需要付费。**

### 2.4 服务器成本三档（对应 PRD N01–N07 待评估项）

| 档位 | 配置                               | 能跑什么                              | 适用阶段         |
| -- | -------------------------------- | --------------------------------- | ------------ |
| 低配 | 4C8G 云服务器（约 ¥150–300/月，以厂商实时价为准） | 门户 + WeKnora + Umami 全部单机 Compose | demo（10/8）足够 |
| 中配 | 8C16G 单机 或 4C8G×2                | 门户与引擎分机，检索并发更高                    | 结项正式版（10/22） |
| 高配 | K8s + Helm                       | 不需要——基金会 1–10 人团队使用，量级到不了         | ❌ 明确不选       |

**省钱要点**：大模型走百炼 API（已购套餐），不自己跑 GPU；WeKnora 的向量化用百炼 Embedding API，不在服务器本地跑模型。**低配单机就能撑住整个营期。**

## 四、接口契约（拼装的"插座标准"）

三份契约放 `docs/contracts/`，**10/4 冻结，之后修改必须走变更流程**（提出 → 影响评估 → 集成负责人拍板 → 群里广播）。

### C2 数据契约：文档（Document）核心字段

| 字段          | 类型       | 必填 | 说明                            |
| ----------- | -------- | -- | ----------------------------- |
| doc_id      | string   | ✅  | 唯一 ID，全局不变                    |
| title       | string   | ✅  | 文件名（检索的主对象）                   |
| category    | enum     | ✅  | 研究报告/政策法规/案例工具/标准（对齐 PRD 四大类） |
| topic       | string[] | ❌  | 主题标签（人工标注，R07 筛选用）            |
| source      | string   | ✅  | 来源机构                          |
| year        | int      | ❌  | 年份（筛选用）                       |
| file_url    | string   | ✅  | 原文件地址（PDF/Word）               |
| file_type   | enum     | ✅  | pdf/word/other                |
| upload_time | datetime | ✅  | ISO 8601                      |

### C3 API 契约（门户后端对前端，节选）

统一约定：`{code, message, data}` 包裹；code=0 成功；错误码段：1001 参数错 / 2001 未登录 / 2002 无权限 / 5000 服务端错。

| 方法 路径                                          | 用途                    | 关键出参                      |
| ---------------------------------------------- | --------------------- | ------------------------- |
| POST /api/auth/register                        | 注册（5 类信息）             | token, user               |
| POST /api/auth/login                           | 登录                    | token, user               |
| GET /api/documents?q=\&category=\&year=\&page= | 列表+文件名检索              | total, items[Document]    |
| GET /api/documents/{doc_id}                    | 详情                    | Document + related[]      |
| POST /api/documents/{doc_id}/download          | 下载（计数）                | file_url                  |
| POST /api/ask                                  | **AI 问答（代理 WeKnora）** | answer, citations[]（引用列表） |
| POST /api/events                               | 埋点上报                  | ok                        |

> **注意 `/api/ask` 是门户唯一暴露的 AI 入口**。前端永远不直连 WeKnora——引擎换掉、接口变了，只改后端 rag-proxy 一处。这就是"粘合层收口"。

### C4 埋点契约

PRD §8 的 8 个事件沿用（page_view / search_submit / search_zero_result / doc_preview / doc_download / ai_ask / ai_answer_view / login_success），统一封装 `track(event, props)`，props 里的字段名以 C4 文档为准。

## 五、拼装保障五件套（怎么保证"一定拼得起来"）

这是回答你最核心的担忧——**"每个人做完之后都可以把它装上来"**。

### 5.1 契约冻结（源头防冲突）

字段名、API 路径、错误码、事件名全部先写死在 `docs/contracts/`。**开发 = 照契约填实现**，不存在"我以为字段叫这个"。10/4 冻结后改契约要走四步变更，改了要广播。

### 5.2 Mock 先行（并行不阻塞）——本方案最重要的一条

**传统拼装失败的死因**：前端等后端、后端等引擎、引擎等数据，一等一星期。

**解法**：F0 地基里做一个 **Mock Server**（一个假后端，按契约 C3 返回假数据）。

```
前端同学：打开 Mock Server 就能开发全部 11 个页面，不等后端
后端同学：按契约写 API，用 Mock 的返回格式做单测，不等引擎
引擎同学：安心部署 WeKnora、导入文档，不等任何人
```

**最后拼装时**，前端把"指向 Mock"的地址改成"指向真后端"，一处配置切换。**因为双方都严格按契约，切换即合体。**

### 5.3 目录即边界（跨界自动报警）

```
widework/
├── docs/            契约（F0 维护）
│   └── contracts/   C2 C3 C4
├── frontend/        F1（Vue）
│   └── src/pages/   一个页面一个目录
├── backend/         F2（FastAPI）
│   └── app/routers/ 一个接口组一个文件
│   └── app/rag_proxy.py   ← 全仓库唯一允许出现 weknora 地址的文件
├── content/         F4（数据与脚本）
├── deploy/          F6（compose/nginx/手册）
├── stats/           F5（Umami 配置与看板）
└── docker-compose.yml
```

CI 加一条检查：`backend` 代码里出现 `weknora` 字样的文件超过 1 个 → 拒绝合并；`frontend` 里出现任何后端内网地址 → 拒绝合并。**边界破坏在 PR 阶段就被拦下。**

### 5.4 PR 闸门（合并不是人情，是检查单）

每个 PR 必须过三关：**① CI 全绿**（能编译、测试通过）→ **② 契约对照清单**（PR 模板里勾选：本次改动涉及哪些契约字段、是否一致）→ **③ 集成负责人审批**。三关全过才能合入 main。

### 5.5 每日集成（集成债不过夜）

每天固定时间（建议晚 9 点）由集成负责人执行：合并当天合格的 PR → main 自动部署到**开发环境**（dev 环境 = 永远是拼起来的最新产品）。**任何时刻打开 dev 环境网址，看到的都是"当前大家拼到什么程度"。**&#x574F;了当天修，不带过夜。

## 六、中心角色：集成负责人（你说的"中间要有一个人"）

| 职责     | 具体动作                           | 频率    |
| ------ | ------------------------------ | ----- |
| 守契约    | 三份契约的唯一维护人；变更请求的受理与拍板          | 随时    |
| 供 Mock | 维护 Mock Server 与契约同步           | 契约变更时 |
| 审 PR   | 对照检查单审查每个 PR（看接口符合性，不抠代码风格）    | 每天    |
| 每日集成   | 合并 + 部署 dev 环境 + 群里播报"今天拼上了什么" | 每晚    |
| 裁冲突    | 两人改了同一处 → 谁保留谁重做，集成负责人说了算      | 出现时   |
| 清占坑    | 任务 72 小时无提交 → 释放回任务池           | 每周    |

**这个角色的工作量**：项目早期（10/1–10/4）较重，之后每天约 30–60 分钟。**建议由技术负责人或 owner 兼任，全营期只此一人，不轮换**（轮换 = 契约解释权混乱）。

> 其余人**不需要**懂 Git 的高深操作——普通成员只需要：领任务 → 建分支 → 改代码 → 提 PR，四个动作，教程见《Git 拼装工作流教程》。

## 七、任务领取机制（自动领任务，不考虑人数）

**任务池 = GitHub Issues，全局进度 = GitHub Projects 看板。**

### 7.1 任务（Issue）的生成与格式

集成负责人按板块批量建 Issue，**每个小块一个 Issue**，格式统一：

```markdown
标题：[F1-02] 登录/注册页开发
标签：板块/F1前端 · 优先级/P0 · 难度/中 · 状态/待领取

## 任务说明
实现登录与注册页（PRD R01、§7.1），含 5 类注册信息表单与隐私提示。

## 交付物
- frontend/src/pages/login/ 目录下全部代码

## 验收标准（3 例）
1. 正确信息注册 → 成功跳首页
2. 缺必填项 → 前端提示且不发请求
3. 已注册手机号重复注册 → 显示 2001 类错误提示

## 接口依赖
- C3 契约：POST /api/auth/register、/api/auth/login
- Mock 已就绪，无需等待

## 领取方式
assign 自己 + 把「状态」标签改为「进行中」+ 评论"我认领"
```

### 7.2 领取规则（防重复、防占坑）

| 规则          | 说明                                    |
| ----------- | ------------------------------------- |
| **一人一坑**    | 同一时间每人最多 2 个"进行中"任务                   |
| **先到先得**    | assign 到谁就是谁的，看板一眼可见，不用群里问            |
| **72 小时释放** | 认领后 72h 无任何提交，集成负责人收回任务回池             |
| **可弃坑**     | 干不了在 Issue 里 comment"释放"，无损面子         |
| **跨板块随便领**  | P3/P4、A/B 组不限，F3 这种部署任务非技术同学也欢迎领（有手册） |

### 7.3 全局看板（GitHub Projects）

`待领取 → 进行中 → 待评审（PR 已发）→ 已合并` 四列。**每人 10 秒能看清：还有什么活、谁在干什么、卡在哪。**

## 八、Git 工作流（GitHub，配合《Git 拼装工作流教程》食用）

| 环节   | 规则                                                   |
| ---- | ---------------------------------------------------- |
| 仓库   | 单仓库 `widework`（GitHub 私有库，免费、协作者不限）                  |
| 主干   | `main` 受保护：禁止直接 push，只能 PR 合入                        |
| 分支命名 | `feat/{Issue号}-{板块}-{简述}`，如 `feat/12-F1-login-page`  |
| 提交信息 | Conventional Commits：`feat: 新增登录页表单校验`               |
| PR   | 模板含"契约对照清单"；标题关联 Issue（`#12`），合并自动关任务                |
| CI   | GitHub Actions：push/PR 自动跑 lint + test + build，红=不许合 |

### 8.1 交付通道设计：不会 Git 命令也能交付（重要）

考虑到大部分成员在 WorkBuddy 里干活、不熟悉 Git 命令，本方案按"上手难度"设三级交付姿势，**全部汇入同一条主干，交付效力与验收标准完全相同**：

| 通道                       | 适合谁     | 成员动作                                       | 上手成本    |
| ------------------------ | ------- | ------------------------------------------ | ------- |
| **姿势 A：GitHub 网页拖拽**（主推） | 90% 的同学 | WorkBuddy 干活 → 下载文件 → 网页上建分支、拖文件上传、点按钮发 PR | **零安装** |
| 姿势 B：GitHub Desktop      | 常干活的同学  | 装官方图形客户端，按钮式操作                             | 装一次软件   |
| 姿势 C：命令行                 | 进阶      | clone → 分支 → add/commit/push → PR          | 学 5 个命令 |

**为什么必须经过本地电脑中转**：实测 WorkBuddy 沙箱**无法直连 github.com**（网络层限制，GitHub 连接器 token 有效但网络不通）。因此标准工作流是「WorkBuddy 生产（用标准交付指令让 Agent 自查契约与验收）→ 下载到本地 → 送上 GitHub」。

**核心配套**：《成果上GitHub-WorkBuddy全员交付教程》（姿势 A/B/C 全流程）——其&#x4E2D;**"标准交付指令"**&#x628A;契约对照、验收自测、commit 规范固化在成员对 Agent 说的话里，拼装纪律前置到生产环节。

> ⚠️ **关于"在 WorkBuddy 里做完直接推 GitHub"**：实测 WorkBuddy 沙箱**无法直连 github.com**（网络层限制），但 GitHub 连接器 token 是有效的。**标准工作流是：WorkBuddy 里干活 → 下载产物到本地电脑 → 本地 Git 推送**。本地 Git 是每个人电脑上装的软件，不受沙箱限制，一次配好全程能用。
