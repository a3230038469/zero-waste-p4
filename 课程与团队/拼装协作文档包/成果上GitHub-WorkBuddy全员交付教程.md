# 成果上 GitHub · WorkBuddy 全员交付教程

> **为谁写**：在 WorkBuddy 对话里干活、但不熟悉 Git 命令的同学（也就是你们大部分人）
> **读完你能**：把你在 WorkBuddy 里做出来的成果，**不打一行命令**，送上 GitHub 拼进产品
> **配套**：《拼装式开发方案 v1.0》
> **版本**：v1.0（2026-10-01）

---

## 〇、30 秒看懂你的工作流

```
① 在 WorkBuddy 对话里，让 Agent 把活干完（你平时怎么干还怎么干）
        ↓
② 让 Agent 按规范整理成果（用本文第二章的"标准交付指令"）
        ↓
③ 把成果文件下载到你的电脑（网页上点下载）
        ↓
④ 送上 GitHub（三选一，本文教三种姿势，新手用姿势 A 就够）
        ↓
⑤ 发起合并请求（网页点两下按钮）
        ↓
⑥ 集成负责人审核合并 → 你的活正式拼进产品 ✅
```

**一个必知的背景**：WorkBuddy 的沙箱**无法直连 GitHub**（实测网络限制）。所以成果必须**经过你的电脑中转一次**——这就是第③步存在的唯一原因，别的地方和传统开发没有任何区别。

## 二、干活：在 WorkBuddy 里的「标准交付指令」（本教程的灵魂）

以后每次在 WorkBuddy 对话里干完活，**别只说"做完了"**，把下面这段话发给你的 Agent（方括号里换成你的信息）：

```
我领的任务是 GitHub 上的 #12 登录/注册页。请按下面要求整理交付成果：

1. 把本任务的全部代码文件整理好，按任务要求的目录结构组织
   （如 frontend/src/pages/login/ 下的文件）
2. 对照下面的任务要求自查一遍：
   [把任务 Issue 里的「验收标准」3 条贴在这里]
   逐条告诉我：通过 / 没通过 / 为什么
3. 你用到的接口字段名，必须是下面这些（不许自己发明）：
   [把任务 Issue 里「接口依赖」部分贴在这里]
4. 最后给我一个交付总结，包含：
   ① 文件清单：每个文件名 + 它应该放到仓库的哪个路径
   ② 一段提交说明，格式：feat: 登录页开发 #12
   ③ 验收自测结果（第 2 条的结论）
```

**为什么要这么做**：契约对照、验收自测、提交规范——拼装纪律全部固化在这一段话里。**Agent 替你把质检做在前面**，集成负责人审 PR 就快，返工就少。

> 💡 任务 Issue 在哪看：GitHub 仓库 → Issues 页签，或直接问群里。

## 三、姿势 A：GitHub 网页拖拽上传（推荐 90% 的同学，零安装）

### 第 1 步：下载成果到电脑

在 WorkBuddy 对话里让 Agent 产出文件后，**把本任务的文件逐个下载**到电脑（建议先建一个文件夹，如 `我的任务/12-登录页/`）。

> 文件少（1–5 个）就逐个下载；文件多就先让 Agent 打包 zip，下载后**解压**再传（GitHub 要的是散文件，不是压缩包）。

### 第 2 步：在 GitHub 网页上建你的分支（1 分钟）

1. 打开仓库页面，点左上角的**分支下拉框**（默认显示 `main`）
2. 直接输入新分支名：`feat/12-login`（格式：`feat/任务号-简述`）
3. 点 **Create branch** —— 你现在站在自己的分支上，怎么改都不影响主干

### 第 3 步：拖拽上传

1. 确认左上角分支显示的是你刚建的名字
2. 点 **Add file → Upload files**
3. **把下载的文件直接拖进那个大虚线框里**
   - ⚠️ 注意：拖进去的文件会传到"当前打开的目录"。先进入正确的目录再拖（点进 `frontend/src/pages/login/` 再上传），或者事后告诉集成负责人路径
4. 下面 commit message 框里填：`feat: 登录页开发 #12`（**必须带 #任务号**，合并后任务自动关闭）
5. 点 **Commit changes** —— 完成！

> 网页上传限制：单次最多 100 个文件、单个最大 25MB。你们的任务颗粒度完全够用。

### 第 4 步：发起合并请求（PR）

1. 点顶部 **Pull requests** 页签 → **New pull request**
2. base 选 `main`，compare 选你的分支 `feat/12-login`
3. 点 **Create pull request**，标题照抄 commit 信息，正文里把 Agent 给你的"交付总结"（文件清单+自测结果）粘进去
4. **Create pull request** —— 收工，等审核

### 第 5 步：等结果

- **绿色 ✓**（CI 通过）+ 集成负责人点 Merge → 群里会播报，你的活拼上了
- **红色 ✗** 或被要求修改 → 看红叉原因，回到 WorkBuddy 让 Agent 修 → 重复第 1–3 步（**还是传到你原来那个分支**，PR 会自动更新，不用重新发）

## 四、姿势 B：GitHub Desktop（常干活的同学，装一次软件后面更省事）

**GitHub Desktop 是 GitHub 官方的免费图形客户端**——Git 的所有命令变成按钮，鼠标点点就行。

### 一次性安装（5 分钟）

1. https://desktop.github.com 下载安装
2. 打开后登录你的 GitHub 账号
3. 点 **File → Clone repository** → 选 `widework` → 选个存放位置 → clone 到电脑

### 每次交付（4 次点击）

1. 把下载的成果文件**复制进 clone 下来的仓库文件夹**对应目录
2. 打开 GitHub Desktop，左边自动列出你的改动
3. 左下角：填一句话 `feat: 登录页开发 #12` → 点 **Commit to main** 旁的分支选择，先建分支 `feat/12-login` 再 commit
4. 点 **Push origin** 推上去 → 点 **Branch → Create pull request**（自动跳网页）→ 点 Create

## 五、姿势 C：命令行（进阶，想成为正经工程师的看这个）

就是《Git 拼装工作流教程 v2.1》那套：clone → 分支 → add/commit/push → PR。**功能上和 A、B 没有任何区别，只是快一点、帅一点。** 建议干两三个任务后自然过渡。

## 六、红线与规则（全通道通用，3 条）

| # | 规则 | 原因 |
|---|---|---|
| 1 | **commit 信息必须带 `#任务号`** | 合并后任务自动关闭、贡献自动统计（结项报告按这个算你的产出） |
| 2 | **只动自己任务目录里的文件** | 越界改别人目录 = 拼装事故，PR 直接被退 |
| 3 | **交付前必过"标准交付指令"的自查** | 契约对不上是返工之王，Agent 自查 1 分钟省你重做 1 天 |

**觉得 4 步还是多？** 就 4 步，比想象中简单——试一次就会了，而且以后每次都一样。真卡住了群里喊一声。

## 七、常见问题

| 问题 | 答案 |
|---|---|
| 为什么不能让 Agent 直接传 GitHub？ | WorkBuddy 沙箱连不上 GitHub（实测网络限制），必须经你电脑中转 |
| 传错文件了怎么办？ | 马上在同一分支再传正确版本（新 commit 覆盖），并在 PR 里留言说明；还没被合并就来得及 |
| 我建错分支名了？ | 无所谓，PR 里说明一下即可，集成负责人合并时处理 |
| CI 红叉是什么？ | 机器自动检查没通过（代码编译不过/测试挂了）。点红叉看详情，回 WorkBuddy 让 Agent 修 |
| 网页上传一次传不完（>100 文件）？ | 分几次传，或换姿势 B；正常单个任务到不了这个量 |
| PR 被要求修改，怎么办？ | 姿势 A：改完重新拖到你那个分支（第 2–3 步），PR 自动更新。**不用关掉重发** |
