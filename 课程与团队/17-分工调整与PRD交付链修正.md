## 一、先把机构要什么看准（我通读了黄正老师那份文档）

### 他们现有的

- **400+ 份 PDF**，主题是垃圾分类、塑料、有机固体废物；类型有政策法规、研究报告、标准、案例工具

| 块 | 具体要什么 |
|---|---|
| **前端页面**（给公众/研究者） | 关键词检索（按文件名）· 分类筛选（类型/主题/年份）· 按年份正倒序 · 预览 + 下载 · **用户上传文件** · **AI 智能问答** · 用户反馈收集 |
| **管理后台**（给基金会内部） | 新增/修改/删除文件 · **审核用户提交的文件** · 统计（访问量、下载次数、AI 提问次数） |

## 二、⚠️ 三个可能"做不完 / 不该做"的地方（必须先跟机构确认）

培训 #04 官方划的红线是：**本月只做网站搭建**，不含 AI Bot、知识库整理、**RAG 增强检索**；层级 ≤5 层；复杂功能"注册会员"和"大批量图片压缩"**二选一**。

拿这条对着机构的需求看：

| 机构要的 | 官方口径 | 我的判断 |
|---|---|---|
| 前端检索 / 筛选 / 排序 / 预览下载 | ✅ 网站搭建 | **能做，而且这是核心** |
| **AI 智能问答（RAG 问答）** | ❌ 明确排除 RAG 增强检索 | **本月不做** —— 这条要提前跟机构讲明 |
| **管理后台（增删改 + 审核 + 统计）** | ⚠️ 没说不能做，但工作量很大 | **要砍小**：统计功能建议先不做；审核功能跟"用户上传"绑在一起 |
| **用户上传 + 审核** | ⚠️ 属于"复杂功能"那一档 | 和"注册会员"性质接近，**要跟机构确认是这次做还是下次做** |

**结论一句话**：机构这份需求是**长期目标**，我们这一个月只能做**其中一块最核心的**。这件事不提前说清，10 月汇报时一定翻车。

> 📌 培训 #04 官方给各组留的第 3 条待办就是这个：**"与客户对接沟通，明确本月项目范围仅限网站搭建"**。跟机构聊访谈时，这件事要放在最前面。

## 三、一个理解偏差要掰正

你说"他们已经有知识库了，后端只需要优化，主要是前端打磨"——**这个理解跟文档写的不一样**，差在两点：

1. **他们的东西在钉钉多维表格里，不是我们系统里的"后端"。** 所以不是"优化后端"，而是**把 400+ 份文件的元数据搬出来，重新做成一个能对外访问的应用**。搬运 + 重建，不是优化。
2. **文档里明确要一个"管理后台"**（给基金会内部增删改、审核用户提交）。这是**新做的东西**，不是现成的。

所以真实工作量比"前端打磨"要重。这一点直接影响分工——**技术这块不是一个人能扛完的**。

## 四、分工方案（按"做什么"分，不按岗位名分）

### 先把三层说清

**这个项目的"后端"不只是表格 —— 还包括给管理员用的操作界面。**

| 层 | 是什么 | 具体活 |
|---|---|---|
| **后端** | ① 数据库：飞书多维表格　② **管理后台**：管理员的操作界面 | 数据字段整理、建表、新增/修改/删除文件、审核用户提交 |
| **前端** | 公众能点能搜的页面 | 检索、筛选、按年排序、文件详情、预览、下载 |
| **设计** | 页面视觉 + 文案 | 配色排版、页面上该说什么话 |

### 三个人怎么分

| 角色（对外） | 人 | 负责什么 | 要交什么 |
|---|---|---|---|
| **技术负责人（后端）** | 丁梓柔 | ① 把 400+ 份文件的字段理清楚、建成数据表<br>② 搭**管理后台**（新增 / 修改 / 删除文件、审核用户提交） | 数据表可用 + 后台能用 |
| **前端负责人**（原设计位） | 徐韶茹 | **公众页面**：检索、筛选、按年排序、文件详情、预览下载 —— 用 AI 搭出来 | 能搜、能看、能下的页面 |
| **技术助手（兼设计）** | 汪月月 | ① **独立搭两个页面**：文件上传页、用户反馈页（自己做出来）<br>② 所有页面的**视觉和文案**<br>③ 配合梓柔做数据：**用 AI 批量处理 400+ 份文件**（从文件名提年份、归主题这类） | 上传页 + 反馈页 + 视觉稿 + 数据清洗结果 |

### 为什么这样分（对每个人意味着什么）

- **韶茹**：她说没设计经验，但**做过个人网站** → 搭页面正好对口，不用碰她不熟的设计
- **梓柔**：她想"主抓技术、深耕网页本身" → 数据 + 后台是完整的后端经验。**如果她其实更想搭页面，可以跟韶茹换**
- **月月**：她说想"能独立搭一个解决实际问题的网页" → **给她两个完整的小页面，自己做出来** —— 这就是她要的技术锻炼；视觉和文案正好配上她"倾向文字"的特点。**不是"帮两位收尾"，是独立交付两块**

> ⚠️ **换岗前先私下问过两位当事人**，别在会上直接宣布。

### ⚠️ 管理后台可能超范围（要跟机构谈）

机构要的"管理后台"（增删改 + 审核 + 统计）**工作量很大**，而培训 #04 说：复杂功能"注册会员"和"大批量图片压缩"**二选一**。

建议：**后台先做最小版**（能新增 / 修改 / 删除就行），**统计先不做**；"审核用户提交"跟"用户上传"绑在一起定去留。

## 五、PRD 的交付链要改：不搞"交接"，两个人同时写

你说的问题是对的 —— 现在的链条是"静柔调研 → 交给瑞泽 → 瑞泽写 PRD → 交"，中间**交接要吃掉一到两天**，而 9.26 就截止。

**改法：不交接，两人并行写同一份文档，各写各的章节。**

登录一个飞书文档（PRD 骨架），分两块写：

| 谁 | 写哪部分 | 内容 |
|---|---|---|
| **胡静柔**（调研） | **事实部分** | 机构现状、用户是谁、访谈发现、需求清单 |
| **奚瑞泽**（产品） | **方案部分** | 做什么 / **不做什么**、功能清单、页面结构、数据模型 |
| **鲍志广**（组长） | 统稿 | 合并 + 交 |

**关键**：瑞泽**不用等访谈结果**。机构已经把需求文档写好了，他可以**直接基于它动手写初稿**；访谈的作用是**确认 + 砍范围**，不是从零采集。

### 还有一个别漏的：PRD 不只是"一份文档"

培训 #04 明确第一周作业包含四样：

> **网站 PRD + 草图 + 前后端各展示什么 + 数据模型**

所以要分给不同人：

| 产物 | 谁 |
|---|---|
| PRD 正文（事实 + 方案） | 静柔 + 瑞泽 |
| **页面草图** | 月月（设计） |
| **数据模型 + 字段设计** | 梓柔 + 韶茹（前后端一起定，字段就是接口） |
