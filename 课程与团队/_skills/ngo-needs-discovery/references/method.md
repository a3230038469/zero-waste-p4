# 方法细则

## 六层分析框架

面对任何机构或业务链路，从这六层下钻，把"卡点"问到具体动作上。

| 层 | 问什么 | 好的答案长什么样 |
|---|---|---|
| 1 业务实质 | 一句话：它到底做什么、靠什么运转 | 能被外行听懂，不含行话 |
| 2 怎么做 | 主要业务链路是什么、创造什么价值 | 能画出三段以内的链路 |
| 3 分几步做 | 拆解每步的具体动作与流转 | 每步是一个可观察的动作 |
| 4 谁用什么工具 | 每步谁在做、用什么、花多久 | 有具体人和具体耗时 |
| 5 遇到什么问题 | 各环节的卡点与痛点 | 指向某一具体步骤，不是"效率低" |
| 6 收益评估 | 解决之后能带来什么 | 能落到一个可观察的指标 |

**用法**：备料阶段用 1—3 层画出骨架并标 `【我们推】`；访谈阶段用 4—5 层逐项核；分析阶段用第 6 层判断值不值得做。

## 连续追问五层

对任何一个抱怨，在原地连问五层"为什么"，直到答案落到"某个具体动作可以改"。

示例（某机构频繁写项目书）：

1. 为什么忙？——写项目书太耗时。
2. 为什么耗时？——每个捐赠方格式不一样，要重写。
3. 为什么格式不一样还都投？——看到机会就投。
4. 为什么看到就投？——没有筛选标准，怕漏掉。
5. 为什么没有标准？——没人负责判断中标概率。

第 5 层的答案才是能动手的地方（建立筛选机制），前四层都不是。

**注意**：每一层下面可能有多个假设，要用对方的话去筛，不能自己挑一个继续问。

## 条件替换验证优先级

把前提换掉再问同一个问题，看对方的反应强度。

- 换资源结构："如果你们的钱 100% 来自政府采购，这件事还重要吗？"
- 换市场体量："如果同行只有 20 家，你还会优先做这个吗？"
- 换时间："如果只能做一件事，你先做哪个？"

**同一个人在不同前提下给出不同答案，说明这个需求不是硬需求**——记下两组答案和前提条件，一起写进痛点清单。

## 访谈提问句式

| 目的 | 句式 |
|---|---|
| 打开话题 | "最近一周，这件事你们大概处理了几次？" |
| 要事实不要评价 | "上一次发生是什么时候，当时谁在处理？" |
| 追问根因 | "是什么让这件事变成这样？" |
| 试探优先级 | "如果把 A 和 B 摆一起，先做哪个？" |
| 验证理解 | "我理解一下——你们缺的其实是 X，对吗？" |
| 收口 | "除了您，还有谁能拍这个板？" |

**避免**：不要问"你们是不是需要一个 XX 系统"——那是在替对方想方案，会把真问题挡住。

## 排优先级的算法

三个维度各打 1—3 分，相乘后排序：

- **出现频次**：每天／每周／每月才发生
- **影响大小**：影响一个人一件事／影响一条链路／影响机构生存
- **能不能验证**：一周内能验证效果／一个月／说不清

得分相同的，选**证据最具体**的那条（有原话、有时间、有人名）。

## 常见判断错误

| 错误 | 表现 | 纠正 |
|---|---|---|
| 把方案当需求 | 对方说"想要个网页"，直接写进需求 | 追问网页要解决什么，写问题不写方案 |
| 把表层当根因 | 写"写作效率低"就收工 | 连问五层，找到能动手的那层 |
| 把个例当共性 | 一次遇到就当成普遍痛点 | 问频次：多久发生一次 |
| 把推断当事实 | 报告里写"机构需要 XX" | 标注来源，无原话的一律 `【我们推，待确认】` |
| 把"都重要"当真 | 对方说都重要就全列 | 用条件替换法逼出排序 |
