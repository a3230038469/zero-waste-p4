# 公益机构需求挖掘

把一家陌生公益机构的真实需求，从"刚接上头"一路做到"交出机构认账的需求报告"。

## 何时使用

用户要开始或推进一次公益机构需求调研时使用：准备访谈、整理访谈记录、判断该先做什么、写需求报告。

## 工作目录与产物

所有产物写入 `客户调研/<机构名>/`，第一次使用时创建该目录。

| 文件 | 内容 |
|---|---|
| 01-机构一页纸.md | 机构怎么运转、我们猜的卡点在哪 |
| 02-访谈提纲.md | 主线问题 + 追问分支 |
| 03-访谈记录.md | 原话级记录 |
| 04-痛点清单.md | 痛点 + 根因 + 优先级 + 证据 |
| 05-需求报告.md | 交给机构的成品 |

**每条信息必须带来源标记**：`【他们说】` 机构原话／`【我们推】` 我们的推断／`【待确认】` 需向机构核实。没有标记的内容不得流入下一段。

**只做第一环**：需求挖掘到"值得解决的问题 + 需求报告"为止。方案设计、产品实现不在本技能范围。

## 第一段 · 备料

**输入**：机构名称；机构给的材料（可选）；公开资料（可选）

1. 创建 `客户调研/<机构名>/` 目录。
2. 读机构给的材料，把机构原话摘出来，标 `【他们说】`。
3. 需要公开资料时，检索机构官网、年报、公众号、媒体报道、项目公告，每条结论附来源。**查不到就写"未找到"**，不用推测补位。
4. 按四个要素给机构做体检：身份与合规／资源获取（钱和人从哪来）／服务转化（钱和人怎么变成服务）／影响力反馈（成果怎么回到捐赠方与公众）。
5. 按七条业务引擎定位可能卡住的环节：筹款／立项书撰写／志愿者招募与管理／活动运营／受益人连接／多方协作／内部合规。猜测一律标 `【我们推】`。
6. 写 `01-机构一页纸.md`，骨架：

```markdown
# <机构名> · 机构一页纸
> 整理日期：YYYY-MM-DD　｜　信息来源：<列出>

## 一句话业务实质
<它到底做什么、靠什么运转>　【他们说/我们推】

## 四要素体检
| 要素 | 现状 | 来源 |
|---|---|---|

## 可能卡在哪条引擎
<1-2 条，说明理由>　【我们推，待确认】

## 未找到的信息
<列出来，后面访谈要问>

## 待向机构核实的问题
1.
```

7. 从"可能卡住的引擎"往外长问题，写 `02-访谈提纲.md`（模板见 @assets/interview-outline-template.md）。

**通过条件**：一页纸里每条结论都有来源标记；访谈提纲每个主线问题下至少挂 2 个追问。

**失败分支**：机构没给任何材料、公开资料也查不到 → 只输出"待向机构核实的问题"清单，明确告知：这段只能靠访谈补，不要编。

## 第二段 · 访谈

**输入**：访谈提纲；现场/线上的对话

1. 开场三句话：说明来意 → 说明会记录 → 请对方随时打断纠正。
2. 按提纲走主线，**重心放在追问**：对方给出一个抱怨，就在原地问为什么，连问五层，追到能动手改的那一层。
3. 用条件替换验证优先级：把前提换掉再问一次（"如果你们的钱 100% 来自政府采购，这件事还重要吗？"），看对方反应判断这个需求是真急还是顺口说的。
4. 结束前必问三句：最想先解决哪个？／除了您还有谁能拍板？／我们理解 A 是 B，对吗？
5. 记录用 `03-访谈记录.md`，保留原话，不改写成结论（模板见 @assets/interview-outline-template.md 第二节）。

**通过条件**：记录里能找到至少 5 处原话；结束前三句都问过。

**失败分支**：对方答不出、含糊、说"都挺重要" → 当场换问法问具体场景（"上周这件事发生了几次？谁在处理？花了多久？"）；仍问不出就在记录里标 `【待确认】`，不许自己填答案。

**现场由用户本人开口。** 本技能不代用户与会话外的人沟通，也不替用户发送消息。

## 第三段 · 分析

**输入**：03-访谈记录.md

1. 把记录里所有抱怨、期待、随口提到的麻烦列成原始条目。
2. 每条挖根因：连续追问五层，直到找到"能动手改、改完上面几条一起解决"的那一层。表层与根因分开写。
3. 对位业务引擎，标出它落在哪条链路上。
4. 排优先级，三个维度各打分后相乘：**出现频次 × 影响大小 × 能不能验证**。无法验证的排到后面。
5. 写 `04-痛点清单.md`（模板见 @assets/pain-point-list-template.md），**每条痛点后面必须挂原话证据**（谁、哪一句）。
6. 写一句话问题定义：`<谁> 在 <什么场景> 下，因为 <根因>，导致 <损失>。`

**通过条件**：每条痛点都有原话；没有原话支撑的一律标 `【我们推，待确认】`；优先级排序有明确依据。

**失败分支**：找不到根因、或根因落不到能动手的层面 → 保留表层问题并标注"根因未确认"，安排第二轮访谈，不硬凑结论。

## 第四段 · 交稿

**输入**：04-痛点清单.md

1. 写 `05-需求报告.md`（模板见 @assets/needs-report-template.md），含背景、问题定义、目标用户、使用场景、功能边界、**不做什么清单**、验证指标。
2. **不做什么清单优先于做什么**：明确列出这一阶段我们不做哪些事，防止后期反复加需求。
3. 附一页"给机构的确认清单"（模板在同一文件的第三节），让机构只需要打勾或回一句话。
4. 先给自己人过一遍，再交给机构。
5. 机构反馈后：按反馈改，不改口径。反馈是温度计，不是判决书。

**通过条件**：需求报告里每条功能都能追溯到痛点清单里的条目；不做什么清单非空；确认清单已交给机构。

**失败分支**：机构反馈"太复杂" → 砍功能，先把最小闭环做出来；机构反复改口径 → 停下来重新确认问题定义，不要跟着改三次以上。

## 能力受限时怎么办

| 情况 | 怎么办 |
|---|---|
| 没有联网检索 | 只用用户给的材料，把"查不到、要问机构"的部分列清楚，标注为受限输出 |
| 无法把文件写进协作文档 | 输出本地文件，由用户自行上传，不宣称已同步 |
| 拿不到会议纪要 | 让用户把记录贴进来，或按记录模板手工整理 |
| 输入是录音 | 请用户提供文字版；本技能不处理音频 |

## 交付前自查

- [ ] 每个文件都在 `客户调研/<机构名>/` 下，命名与表格一致
- [ ] 一页纸、痛点清单、报告里每条信息都有来源标记，`【我们推】` 与 `【他们说】` 没混
- [ ] 痛点清单每条都有原话证据和具体出处
- [ ] 需求报告的每条功能都能追到痛点清单
- [ ] "不做什么清单"非空且具体
- [ ] 一句话问题定义写出来了，且指向一个能动手的根因
- [ ] 没有替用户对外发送任何消息

## 停止条件

出现以下情况立即停下并告知用户，不用推测内容顶替：

- 机构信息、访谈记录或痛点证据缺失，且用户无法提供
- 用户要求把未经确认的推断写成机构的需求
- 用户要求代其向机构或群聊发送内容
- 任务实际落在方案设计或产品实现阶段（不属于本技能范围）
