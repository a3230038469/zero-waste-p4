# 访谈痛点分析

把一段访谈记录、群聊或对话文字，变成一张能拿去决策的痛点清单。

## 何时使用

用户手上已经有对话材料、需要判断"他们真正缺的是什么"时使用：访谈刚结束、群聊里攒了一堆反馈、机构材料读完想提炼问题。

## 输入与输出

**输入**：访谈记录、会议记录、群聊文字、机构材料——**文字形式**（录音请先自行转成文字）
**输出**：痛点清单，含每条痛点的表层现象、根因、所在环节、原话证据、优先级、一句话问题定义

## 步骤

1. 通读全部材料，把"抱怨、期待、随口提到的麻烦"逐条摘出来，**保留原话**，不改写。
2. 合并同类项：说法不同但指向同一件事的，合并成一条，各自的原话都保留。
3. 每条挖根因：从表层现象连续追问五层"为什么"，直到找到"某个具体动作可以改"的那一层。表层与根因分两栏写。
4. 找使用条件替换验证过的条目：把材料里"换了前提就改口"的段落标出来，两组答案和各自前提一起记录。
5. 对位业务环节，标出它落在哪条链路上：筹款／立项书撰写／志愿者招募与管理／活动运营／受益人连接／多方协作／内部合规。
6. 排优先级：**出现频次 × 影响大小 × 能不能验证**，各打 1—3 分后相乘。无法验证的排后面。
7. 写一句话问题定义：`<谁> 在 <什么场景> 下，因为 <根因>，导致 <损失>。`
8. 输出痛点清单（模板见 @assets/pain-point-list-template.md）。

## 通过条件

- 每条痛点都挂着原话证据（谁、哪一句），能指回原始材料
- 表层现象和根因分列，没有把判断混进原话
- 排序有明确分数依据，同一批痛点用同一套口径
- 没有原话支撑的条目一律标 `【我们推，待确认】`
- 一句话问题定义指向一个能动手的根因

## 失败分支

| 情况 | 怎么办 |
|---|---|
| 材料里全是评价、没有事实 | 输出"需要补问的事实清单"，明确告知现有材料不足以判断痛点 |
| 找不到能动手的根因 | 保留表层问题并标注"根因未确认"，建议再访一轮，不硬凑 |
| 两个来源互相矛盾 | 并列两种说法、各自出处，标为待确认，不替用户选一个 |
| 材料太碎、指向很多方向 | 先按频次粗排，把出现次数最多的三条拎出来做深挖，其余列为观察项 |
| 输入是录音或音频 | 请用户先转成文字；本技能不处理音频 |

## 边界

- **只做分析，不做沟通**。不替用户向机构或群聊发送任何内容。
- 不编造材料里没有的痛点和数据；不把用户的主观判断改写成机构的需求。
- 不评价机构做得好不好，不给公益项目打分。

## 交付前自查

- [ ] 每条痛点都有原话和出处
- [ ] 表层与根因分列，根因指向可动手的动作
- [ ] 优先级分数可复核，口径一致
- [ ] 没有原话的条目已标 `【我们推，待确认】`
- [ ] 一句话问题定义已写，且只有一个主根因
- [ ] 材料里的矛盾之处已并列标出，未被抹平
- [ ] 输出中没有出现凭据或隐私信息

## 停止条件

- 用户要求把推断直接写成机构的正式需求
- 材料不足以支撑任何根因判断，且用户无法补充
- 用户要求代其对外沟通或发送内容
