# 分析细则

## 从材料里摘什么

| 摘 | 不摘 |
|---|---|
| 具体的时间、频次、人数 | 泛泛的"效率低""不太好" |
| 谁在做、花多久 | "大家都觉得" |
| 上一次发生了什么 | 假设性的"如果要是有" |
| 停顿、改口、"其实吧……"后面的半句 | 客套话与场面话 |

**纪律**：原话栏只放对方说的字，一个字不改；我们的理解放另一栏。

## 追问链条的记录方式

```markdown
表层：<对方原话>
├─ 为什么？ → <回答>
│  ├─ 为什么？ → <回答>
│  │  ├─ 为什么？ → <回答>
│  │  │  ├─ 为什么？ → <回答>
│  │  │  │  └─ 为什么？ → <回答> ← 能动手改的一层
├─ 为什么？ → <另一条假设的回答>
└─ 为什么？ → <第三条假设>
```

每一层下面可能有多个分支。**只有被材料证据支持的分支才继续往下走**，其余标为"无证据，待问"。

## 条件替换的判读

把材料里"换了前提就改口"的地方挑出来：

| 条目 | 前提 A 下的回答 | 前提 B 下的回答 | 结论 |
|---|---|---|---|
| <需求> | "最想做这个" | "那还是先做另一个" | 不是硬需求，优先级待定 |

**只有一个前提下也坚持要做的，才是硬需求**；两个前提下答案不同的，写进"条件依赖"一栏，不排到第一位。

## 影响大小怎么分档

| 分 | 判断标准 |
|---|---|
| 3 | 影响机构生存或主要收入来源 |
| 2 | 影响一整条业务链路（多个角色、多个环节） |
| 1 | 只影响一个人或一个环节 |

## 能不能验证怎么分档

| 分 | 判断标准 |
|---|---|
| 3 | 一周内能拿出可观察的结果 |
| 2 | 一个月内能验证 |
| 1 | 说不清怎么算成功 |

**1 分的条目不要排在前面**：测不出效果的需求，做完也没法证明有价值。

## 常见误判与纠正

| 误判 | 表现 | 纠正 |
|---|---|---|
| 把情绪当痛点 | "他们很焦虑" | 追问焦虑指向哪件具体的事 |
| 把方案当需求 | "想做一个工具" | 问工具要解决什么，写问题不写方案 |
| 把一次当常态 | 只出现一次就排前面 | 先问频次 |
| 把负责人当全体 | 一个人的抱怨当成机构共识 | 标出这是谁说的，注明是否只此一人 |
| 抹平矛盾 | 两种说法选一个当结论 | 并列两种说法与出处 |
| 过度归因 | 直接写"管理混乱" | 退回到可观察的动作层面 |

## 输出时要写清的元信息

- 材料来源（谁说、什么时候说、什么场合）
- 分析日期
- 哪些结论是原话直接支持的，哪些是我们的推断
- 材料未覆盖的部分（哪些环节这次完全没聊到）
